ai-task-runner

Flow diagrams

Six views of the same machine: a resumable bridge between a task manager and a coding agent. Each page is standalone and interactive — pan, zoom, search, trace a relationship, step through the guided views, switch light/dark, or export. Start with the system map, then follow a ticket through the two zoomed paths.

01Architecture

System map

What the pieces are and which seam each one sits behind: providers, agents, vcs, the local SQLite store and the per-repo brain.

  • pipeline.py names no tracker, agent or host
  • Local state vs. the one shared AI State field
  • Where redaction happens on the way out
 02Workflow

One tick

What a single ai-task-runner run actually does: day and window gates, daily limits, advance in-flight rows first, then triage what is new.

  • Every task moves at most one step, then the process exits
  • Cheap bookkeeping runs before any LLM call
  • Orphan detection: never adopt another machine's work

03Workflow

New ticket → queued

The denylist, the tool-less triage call, routing to one or more repositories, the scope gate and the analyst's grounded plan.

  • Hard rules overrule the model, every time
  • Triage judges text only — it cannot open the repo
  • Re-triage keeps the repo set so no branch is stranded
 05Sequence

Ticket → approved plan

The same stretch as call traffic: who calls whom, in which tick, and where the process stops and starts again.

  • Each band is a separate short-lived process
  • reason() vs. work() with read-only planner tools
  • Approval is an ordinary ticket comment

Zoom: the back half

04Workflow

Queued → merged

The implementer, the independent reviewer that runs before any PR exists, the revision loop, the CI fix loop and every escalation.

  • One agent per repo, held by a lease
  • Crash budgets reset on each clean hand-off
  • Only an approving review writes to the brain
 06Sequence

Approved plan → merged PR

Implement, commit, push, review, open a draft PR, then poll it tick by tick until a human merges.

  • The agent edits; the runner commits, pushes and opens the PR
  • Worktrees are isolated, never your own checkout
  • Polling is never waiting — pending CI just ends the tick

How these were made

Each page is generated from a small typed JSON specification in specs/ and validated against layout, crossing, label-clearance and desktop-readability checks before it is written. To change a diagram, edit its spec and re-render it rather than hand-editing the HTML.

node ~/.claude/skills/archify/bin/archify.mjs deliver workflow \
  docs/flow/specs/04-build-review-ship.workflow.json \
  docs/flow/04-build-review-ship.html --quality showcase

The live state graph itself stays authoritative in runner/graph.py; ai-task-runner graph prints it as Mermaid straight from the same TRANSITIONS table the runtime uses.
